1. Executive summary
Stage A is the final design for a serious, local-first India equity research engine intended for personal use. The 
engine is designed to ingest official/public Indian market and filing data, normalize everything into a point-in-time 
warehouse, compute technical, fundamental, governance, macro, derivatives EOD, benchmark-relative, and 
event/news features, score stocks deterministically across multiple horizons, and then hand only the structured 
result to a local LLM for explanation.
The most important architectural choices are: (a) Indian equities only; (b) ISIN as the canonical security key; (c) 
XBRL-first fundamentals; (d) exchange disclosures before media headlines; (e) local filesystem + Parquet + DuckDB 
instead of a database-heavy stack; (f) deterministic scoring before LLM narration; and (g) explicit point-in-time 
fields to prevent future-data leakage in research and backtests.
Stage A can be built with zero mandatory recurring subscriptions if you remain on public/official sources and local 
compute. Optional paid items exist, but they are not prerequisites for the first robust version. That makes Stage A 
the highest-leverage build because it stays powerful while remaining inexpensive and operationally simple.
What Stage A will deliver
 Daily research-ready snapshots for Indian stocks in the chosen universe.
 Technical, fundamental, governance, macro, benchmark-relative, derivatives EOD, and event/news features.
 Short-term, medium-term, and long-term scores with confidence and conflict handling.
 A structured recommendation object for research use: bullish / neutral / bearish with abstain support.
 A local LLM explanation that cites only the structured evidence inside the snapshot.
 A repo and storage layout that can later grow into Stage B or cloud deployment without redoing the core model.
What Stage A will not attempt
 No exchange-licensed real-time public distribution product.
 No low-latency intraday or tick-data plant.
 No premium paid news, analyst consensus, or transcript feeds as mandatory dependencies.
 No personalized investment-advice workflow. Stage A is a research engine, not a suitability engine.
 No reliance on the LLM for numeric computation, signal generation, or portfolio optimization.
2. Scope, goals, non-goals, and assumptions
2.1 Scope
 Asset class: listed Indian equities. Use NSE and BSE public surfaces, joined primarily through ISIN.
 Refresh model: daily market and filing batch after close, with optional hourly refresh for event/news inputs.
 Primary usage: personal research and decision support on a local machine.
 Primary output: stock_snapshot JSON plus a human-readable explanation.
2.2 Primary goals
 Analyze an Indian stock from multiple lenses with one reusable engine.
 Use free or publicly accessible official sources wherever possible.
 Be robust and auditable even though the first deployment is local and personal.
 Make later scale-up easy by preserving strong schemas, lineage, and module boundaries from day one.
2.3 Working assumptions
 You are comfortable running Python locally and keeping raw data on local storage.
 End-of-day analysis is acceptable for Stage A; low-latency live trading is deferred.
 You are willing to use optional one-off paid access (for example MCA documents) if it materially improves data 
completeness.
 GitHub is for code, docs, configs, tests, and small fixtures only - not the historical data lake.
 AWS is optional and only for backup or convenience; Stage A must remain fully functional without it.
2.4 Design principles
 Structured source first: XBRL > CSV/XML > HTML > PDF fallback.
 Official source first: exchange and regulatory filings before media narratives.

avoid the most common early failure mode in personal quant projects: spending energy on infrastructure that is far 
more complex than the actual data and research problem.
4. Architecture overview
The architecture is a modular monolith for Stage A. That means one repo, clear module boundaries, typed 
interfaces, and a local run model, but without the operational tax of a microservice mesh. Each connector, parser, 
feature family, and scoring component lives in its own module so it can be replaced later without changing the 
whole system.

4.3 Layered data model
 Raw / Bronze: immutable source artifacts exactly as downloaded or captured.
 Normalized / Silver: table-level cleaned records with canonical keys, types, timestamps, and lineage.
 Snapshot / Gold: feature snapshots, scores, and final stock_snapshot JSON objects.
4.4 Point-in-time rule
No record is complete without timing metadata. At minimum, every business fact should carry as many of the 
following as make sense: trade_date, period_end, filing_date, available_at, as_of_date, retrieved_at, source, 
source_url, document_hash, restated_flag, and parser_version. This is critical for honest research, because 
quarterly results become usable when they are filed, not when the quarter ended.

exists.

6.5 Universal connector contract
discover() -> list[SourceObject]
download(source_object) -> RawArtifact
validate(raw_artifact) -> ValidationResult
store_raw(raw_artifact) -> RawArtifactRecord
parse(raw_artifact) -> list[NormalizedRecord]
normalize(records) -> CanonicalTableRows
upsert(rows) -> WarehouseWriteResult
Every connector follows the same flow: discover what is available, download the raw artifact, validate and hash it, 
store it immutably, parse it, normalize it, and then write the canonical rows. This keeps the ingestion layer 
consistent and testable.
7. Local data architecture and storage model
For Stage A, the cleanest storage stack is raw files on local disk, normalized Parquet datasets, and DuckDB views / 
tables on top. This gives you fast analytics, simple backups, and easy reproducibility without running a separate 
database server.
7.1 Storage layers
 data/raw - immutable source artifacts exactly as captured.
 data/silver - normalized Parquet tables partitioned by logical time keys.
 data/gold - feature snapshots, score snapshots, stock_snapshot JSON files, and explanation outputs.
 data/cache - API response caches, temporary renders, and parser scratch space.

This convention makes the raw store append-only, easy to diff, and easy to recover from if a parser changes later.
7.4 Partitioning guidance
 price_daily: partition by year and month of trade_date.
 financial_facts: partition by filing_year and statement frequency.
 announcements / corporate actions: partition by event date.
 macro_series: partition by source and series_code.
 feature_snapshots / score_snapshots: partition by as_of_date.
7.5 Why DuckDB is the right Stage A warehouse
 Excellent local SQL performance on Parquet.
 Minimal operations overhead.
 Easy ad hoc research from notebooks or CLI.
 Natural fit for a single-user analytical workload.
 Straightforward later migration to cloud object storage patterns if needed.
8. Canonical schemas
This section defines the canonical logical schema for Stage A. The goal is not to mirror each source exactly. The goal 
is to store clean, point-in-time, analysis-ready records that preserve lineage back to the source artifact.
8.1 Shared conventions
 All table names use snake_case.
 IDs are text UUIDs or deterministic composite keys depending on the table.
 Numeric measures use DECIMAL for stored values unless the field is naturally integer.
 Timestamps are UTC where possible.
 Booleans are explicit booleans; do not use 0/1 strings.
 JSON fields are permitted only for sparse or nested outputs such as evidence arrays and LLM output payloads.

10. Event and news intelligence layer
The event layer is a first-class part of Stage A because Indian stocks react not only to company fundamentals and 
price action, but also to corporate disclosures, RBI policy, budgets, elections, oil shocks, FX moves, and geopolitical 
conflict. This layer translates raw events into structured stock-level impact signals instead of letting the LLM guess 
from headlines.
10.1 Event source groups
 Issuer-specific: NSE / BSE corporate announcements and actions.
 Indian policy: PIB, RBI, Union Budget documents, ECI event/result pages.
 Global and geopolitical: GDELT and optional supporting APIs.

ingest -> deduplicate -> classify -> entity-link -> map to exposure channels
-> score importance / novelty / polarity / confidence -> emit stock-level event_signals

10.4 Event scoring dimensions
 Source reliability: exchange and regulator > government > open global news > optional media API.
 Novelty: whether the item is materially new or a duplicate / commentary echo.
 Materiality: likely economic importance of the event.
 Time horizon: short-lived shock vs medium-term policy change vs long-term structural shift.
 Exposure fit: how strongly the event maps to the stock or its sector.
 Confidence: certainty of the mapping rule and data quality behind it.
10.5 Why this layer is superior to raw sentiment
A raw headline polarity score is too weak for serious stock research. For example, a geopolitical conflict may be 
"negative" in the abstract, but its real stock impact depends on oil prices, currency, import dependence, regulated 
pricing, and sector structure. The event layer therefore converts external events into exposure-aware signals 
before they touch the score.
11. Signal, scoring, and decision layers
11.1 Signal generation
 Signals are deterministic rules over features, not LLM outputs.
 Every signal should store: name, direction, threshold logic, horizon, confidence, decay, and evidence references.
 Conflicts are explicit first-class outputs. Example: strong value but weak trend, strong fundamentals but negative 
governance events.
11.2 Horizon model
Horizon Definition Primary drivers
Short 5-20 trading days Technical, events, derivatives EOD, and 
near-term announcement context 
dominate.
Medium 1-3 months Blend technical, revisions-like proxies, 
event carryover, and benchmark-relative 
context.
Long 6-12 months Fundamental quality, valuation, 
governance, and structural macro / 
sector signals dominate.
11.3 Score model
 Keep component scores separate: technical, fundamental, governance, macro, event, derivatives, peer-relative.
 Compute a composite score per horizon through a configuration-driven weighting layer.
 Maintain a separate confidence_score that is reduced by missing coverage, stale inputs, and unresolved signal 
conflicts.
 Support an abstain state when confidence is below threshold or when conflicting evidence is too severe.

12. Local LLM integration layer
The LLM should be treated as an explanation engine, not a pricing engine. Its inputs must be small, typed, and 
structured. Its outputs must be schema-validated before being shown or stored.
12.1 Input contract
 Stock identity and snapshot metadata.
 Top features and component scores by horizon.
 Top positive and negative drivers.
 Conflict matrix and explicit risk flags.
 Coverage and missing-data notes.
 Evidence identifiers back to source tables and filings.
12.2 Output contract
 Short-term outlook paragraph.
 Long-term outlook paragraph.
 Why the model likes / dislikes the stock.
 What the major risks are.
 What evidence is conflicting or missing.
 A restrained language policy: never claim certainty or guarantees.
12.3 Guardrails
6. Do not let the LLM read raw OHLCV or raw filings directly.
7. Do not ask the LLM to calculate indicators, DCFs, or valuation multiples.
8. Reject outputs that do not match the expected schema.
9. Log model name, prompt version, input hash, and validation results.
10. Render the final explanation only after deterministic decision outputs exist.
12.4 Local model sizing guidance
Because the model only interprets structured snapshots, Stage A does not require a giant model. A strong 7B-14B 
instruction model with reliable JSON-following behavior is usually sufficient. If you do not have a GPU, you can still 
run quantized local models on CPU, but the explanation step will be slower. The core engine itself remains CPU-
friendly.

17. Risks, limitations, and mitigations
Risk Mitigation
Public page structure changes Prefer structured downloads and RSS. Keep parser fixtures and 
versioned adapters. Use HTML scraping only when needed.
Source throttling or anti-bot controls Use respectful cadence, headers, retries, and local caches. 
Reserve browser automation for fallback only.
Incomplete or inconsistent filings Use XBRL-first logic, retain raw documents, and allow optional 
MCA supplementation.
Future-data leakage in research Enforce available_at and filing_date handling everywhere.
Overconfidence in scores Separate score from confidence and maintain an abstain state.
LLM hallucination Never let the LLM compute from raw data. Validate outputs 
against schema.
GitHub repo bloat Keep data and model artifacts out of GitHub; use local storage 
and backups.
Underpowered local machine Keep batch jobs incremental and use smaller local models or 
CPU-only inference if needed.
The main hidden risk in projects like this is not missing one more indicator. It is weak data lineage and timing 
discipline. If Stage A gets the raw store, point-in-time logic, schemas, and event mapping right, everything else 
becomes easier to improve later.
